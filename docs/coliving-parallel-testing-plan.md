# 合租房大脑：测试-开发循环怎么并行化

> **这是一份计划文件，不是已经实施的东西。** 用户明确说了"以后我想实施了就
> 会叫你按这个文件干活"——写这份文件本身不改任何代码。执行前请先跟用户过一遍
> 现状是否有变化（尤其是模型选型、数据库、部署环境这几块，变化最快）。

## 背景：现在的循环为什么慢

2026-09-04 那次自主循环，25 轮测试用了一个下午。拆开看，每一轮做的事：

1. 想一个新场景（WebSearch 找 Reddit 素材）
2. 手写一个一次性的 `scripts/_tmp-*.ts`，构造测试屋和对话
3. `pnpm coliving:db --purge` 清空数据库（**这一步是唯一的串行点**——
   下一轮必须等这一轮的数据清干净）
4. 跑 `runColivingTurn`，等真实模型调用（deepseek-v4-flash 实测 38–60 秒
   一轮，带批判器复核、可能的打回重写，一个场景两轮对话经常要 2–3 分钟）
5. 逐字读输出，对照三层准则人工判断
6. 查数据库核对 case_file / event / communication 等表
7. 找到真 bug 就定位根因、改代码、`tsc`/`brain:inspect` 验证、
   跑 2–3 次复测确认稳定、写 commit、推送
8. 写一条 AGENT_LOG.md 记录
9. 清理临时脚本，进入下一轮

**这九步里，只有第3步（purge）是真正需要串行的**——而且严格说也不是必须
串行，是图省事选的清空重来，不是架构上非如此不可。第4步（等模型跑完）和
第5–6步（人工审查）加起来占了每轮的大部分时间，而这两步**本质上是彼此独立
的、可以并行的工作**：25个场景互不依赖，同时起跑没有任何冲突（各自的
测试屋、各自的 household_id，数据库层面天然隔离）。

真正卡住并行的是**这套流程被设计成了一个人（我）从头串到尾**：
出题、跑测试、读结果、判断合不合规、定位根因、改代码、验证、写记录——
七件性质完全不同的活，全挤在一条线上，前一件不做完，后一件无法开始。

## 目标

不是"跑得更快"这么简单，是**把"测试用例的数量"和"验收要花的时间"解耦**。
用户提到业务规模变大后真实用例会多到"不是互联网软件时代能比拟的"——
如果验收速度还是线性跟着用例数走，用例越多，反而越不敢多测。目标是：

- 测试用例数量翻十倍，运行这批测试花的时间基本不变（并行跑批）
- 判断"这条输出对不对"的工作也能并行，不堵在一个人脑子里
- 每一轮抓到的真 bug 不再是"测完就扔"的一次性脚本，而是永久沉淀成
  回归语料——下次改代码，自动重新验证过去踩过的所有坑，不用人再想起来
- 真实生产环境冒出来的边界案例（比如这次的"上线流程从没测过"、
  Twilio 幂等问题）有地方回收，变成语料库的一部分，不是查完就忘

## 行业参考（挑对这个项目有用的部分讲，不铺开讲）

AI 产品这几年在"提示词/智能体测试"上收敛出来的几个做法，跟这里的处境
高度相关：

- **语料先于脚本**：成熟的 eval 框架（OpenAI Evals、Anthropic 自己的
  eval harness、开源的 promptfoo / Braintrust / LangSmith 这类）
  都不是"每次现写一段跑一次"，而是把测试场景存成结构化数据（YAML/JSON），
  代码只负责"读语料、跑、判分"。语料可以增量累积、可以复用、可以被
  多个不同的 runner 跑（比如本地跑一遍、CI 跑一遍）。
- **跑批默认并行**：既然每条用例互相独立，运行阶段就是纯粹的并发
  I/O（都是在等模型接口返回），没有理由串行。这些框架默认给一个
  并发度上限（避免打爆模型接口的速率限制），然后交给 `Promise.all`
  / 类似的并发原语。
- **判分分层**：**能用代码判的绝不用模型判**（长度、格式、有没有编号
  泄漏、数据库落地是否一致这类结构性检查——这正是我在循环里手动做的
  那部分数据库核对工作），模型判分（LLM-as-judge）只用在真正需要
  语义理解的地方，而且判分本身也是批量、并行跑的，不是一条条现判。
- **回归语料库只增不减**：每抓到一个真实 bug，对应的那条用例就**永久
  留在语料库里**，成为以后每次跑批都会重新验证的一条基线。这是这些
  框架能长期"不走回头路"的关键——不然改了一个地方，几周前修过的
  bug 悄悄回归都发现不了。
- **生产事故反哺语料**：越成熟的产品，"新增测试用例"的主要来源会从
  "凭空设计场景"逐渐变成"生产里真实出过问题的对话，脱敏后收进语料库"。
  这次用户自己上线体验时踩到的"上线流程从没测过""名册确认过期快照"
  这两个 bug，正是这个模式的第一个例子。
- **数据库/环境隔离用分支，不用清空重来**：现代托管数据库（这个项目用
  的 Neon 本身就支持）普遍提供"秒级建分支"的能力，CI/测试场景常见做法
  是每一批测试用一条独立分支起跑、跑完就丢，而不是共用一个库、每次
  清空重来。这个项目目前用的是"共用一个测试库，跑之前 purge"，够用，
  但不是并行度上不去的时候的唯一选项。

## 分阶段方案

**阶段一收益最大、改动最小，值得优先做。后面几个阶段按实际需要再上，
不必一次性建完。**

### 阶段一：语料化 + 并行跑批（预计把"一下午"压到"几分钟"）

把 `scripts/_tmp-*.ts` 这种一次性脚本，换成结构化的场景语料 + 一个
批量 runner：

```
lib/chat/coliving/evals/
  scenarios/
    2026-09-cat-allergy.json       # 第9轮那种猫过敏场景
    2026-09-thermostat-war.json    # 第10轮恒温器
    ...（每个场景一个文件，人名/对话内容/素材来源都在里面）
scripts/coliving-eval.ts           # 批量 runner，风格照抄 search-eval.ts
```

**场景文件的最小结构**（不需要多复杂，够用就行）：

```json
{
  "id": "cat-allergy-2026-09",
  "source": "r/badroommates —— 猫夜里钻被窝，室友对猫毛过敏",
  "household": { "label": "…" },
  "people": [
    { "phone": "+1555...", "name": "阿哲", "role": "tenant" },
    { "phone": "+1555...", "name": "小林", "role": "tenant" }
  ],
  "turns": [
    { "from": "+1555...002", "text": "小林养的猫夜里总是溜进…" },
    { "from": "+1555...003", "text": "Jon Jon 一直都是这样自由进出的…" }
  ]
}
```

**runner 的关键点**：

- 不再 `pnpm coliving:db --purge`。每个场景用自己独立的
  `createTestHousehold(scenario.id)`，household 之间靠 `household_id`
  天然隔离，purge 这一步彻底不需要了——这就是解开当前那唯一串行点的
  办法。
- 并发跑，带上限（比如 `--concurrency 6`，避免同时打爆模型接口和数据库
  连接池）。跑法参考项目里已经有的 `search-eval.ts` 那套
  `--limit`/并发处理的写法，风格保持一致。
- 每个场景跑完，**结构化落一份结果**（不是打印到终端就完事）：
  对话原文、`toolsUsed`、critic 拦截记录、DB 里 case_file/communication
  的核对结果，存成 JSON，供下一阶段用。
- 跑完批量清理：**不删场景语料**（那是要沉淀的），只清理这次跑批产生的
  测试屋数据（或者干脆不清理，反正靠 `is_test=true` + household_id
  隔离，留着也不碍事，磁盘成本可以忽略）。

### 阶段二：结构性检查自动化（脱离 LLM 判断）

现在循环里，我每轮都要手动查库确认这几件事：

- `communication` 表的 `error` 字段有没有说明拦截原因（不能只看 `status`）
- `case_file` 有没有为同一件事重复开出好几条
- `rule` 表的 `agreed_by`/`objected` 跟 `status` 对不对得上
- 出站消息声称"已联系"时，对应的 `contactPerson` 调用是否真的成功

**这些全部是确定性的、可以写成脚本直接判的检查**，不需要任何模型参与。
把它们写成 `scripts/coliving-eval.ts` 里的一组断言函数，跑批的时候
自动跑、自动标红，不用人（或者我）每轮现查。这一步做完之后，"数据库
落地是否正确"这类第9/10/12/15/18轮抓到过的 bug，理论上跑批当场就能
标出来，不用等人工发现。

### 阶段三：语义/合规判断的并行化

结构性检查过了，不代表内容没问题——"这条回复有没有指控报告问题的人""
有没有暗示驱逐""语气是通知还是商量"这类判断，还是需要理解语言，绕不开
LLM 或者人来判。这一层怎么并行：

- **不是每条场景都要过一遍完整的三层准则人工审查**。跑批之后，先看
  阶段二的结构性检查结果——干净的场景可以只抽样复核，真正要逐字看的
  是结构性检查已经标红、或者这次改动直接相关的那几条。
- 需要逐条看的场景，**用 Claude 的子代理（Agent 工具）批量分发**，
  不是我一个人挨个看。比如 20 条场景要复核，分成 4 组，一次性起 4 个
  子代理并行看，每个子代理只对着自己那几条场景 + 三层准则文本，输出
  结构化的发现（合规/违反哪一条/严重程度），最后我做一次汇总和优先级
  排序。这跟现在"我一个人顺着读 25 轮"是同一个判断力，只是把"读"这个
  动作铺开成并行的。
- 这一步仍然遵守用户的原话："验收的动作你想办法走你的额度，别走
  vercel gateway"——子代理消耗的是这个会话自己的额度，不是给
  `runColivingTurn` 本身多加一层模型调用。

### 阶段四：修复阶段的并行化

如果一次跑批抓到了好几个互相独立的真 bug（不同文件、不同根因），
修复也可以并行，用 `isolation: "worktree"` 起多个子代理，每个子代理
在自己的 git worktree 里定位、修复、验证一个 bug，互不干扰对方正在
改的文件。全部完成后：

- 我依次 review 每个 worktree 的改动（不能跳过这一步——子代理的改动
  要经过检查再合并，尤其是提示词层面的改动，CLAUDE.md 那"改大脑提示词
  前三问"的纪律不能因为并行就松掉）
- 合并进主分支，**跑一次全量语料回归**（阶段一的批量 runner 再跑一遍
  全部场景，包括没直接相关的），确认没有互相踩踏
- 一次性提交、推送，AGENT_LOG.md 写一条汇总记录（不用像现在这样
  一轮一条，可以是"这批跑了 N 条语料，发现 M 个真 bug，逐个说根因
  和修法"）

如果只抓到一个 bug，走现在这套单线修复流程就够，不用为了并行而并行。

### 阶段五：回归语料库只增不减

每次跑批抓到的**真 bug**，对应的场景文件从"跑批用完的临时数据"升级成
"永久语料"——就是阶段一里存到 `lib/chat/coliving/evals/scenarios/`
下的那些 JSON 文件，正常 commit 进仓库，不删除、不覆盖。往后每次跑批
默认把语料库**全量**跑一遍（不是只跑这次新加的），这样任何代码改动
（哪怕看起来跟某个老 bug 毫无关系）都会自动重新验证过去踩过的所有坑。

这跟项目里已经有的 `search-eval.ts` / `comment-reply-eval.ts` /
`redact-eval.ts` 是同一套思路（CLAUDE.md 里那张表列的评测脚本），
`coliving-eval.ts` 应该照着同样的风格建、放进同一张表里，"按需跑，
不是每次改动都要跑"这条纪律也适用。

**生产事故的语料回收**：这次用户自己上线体验时发现的两个 bug（上线
流程从没测过、名册确认用了过期快照），复现脚本就是天然的候选语料——
以后类似情况，先把复现步骤存成一条场景文件，再动手修，语料库就自动
多了一条"上线流程"这个此前完全没覆盖的类别。

### 可选、暂不需要现在做：数据库分支隔离

现在的方案（共用一个测试库、靠 `household_id` 隔离、不再 purge）在
并发到几十上百条场景的量级应该够用——Neon Postgres 单条连接池扛得住
这个规模的并发写入，household 之间没有共享状态。

如果以后跑批规模真的大到"共用一个库"本身成为瓶颈（比如要跑几千条
场景、想要每次都是绝对干净的白板状态、或者想让多个互不信任的并行
分支各自独立验证），可以上 Neon 的数据库分支能力：跑批开始时建一条
临时分支，几个并行 worker 各自用自己的分支，跑完直接丢弃分支，
不需要清空重来。这是"到了那个规模再上"的选项，不是现在就要建的
基础设施——过早建这套会话把简单问题复杂化，不符合这个项目一贯的
"少而精"取向。

## 具体要新建/修改的文件（真正动手实施的时候照这个清单走）

- `lib/chat/coliving/evals/scenarios/*.json`（新建目录，语料库，
  从现有的 25 轮场景开始迁移几个有代表性的，不用一次性搬完）
- `lib/chat/coliving/evals/schema.ts`（新建，场景文件的 TS 类型定义，
  跑 runner 之前先用这个校验语料格式对不对）
- `scripts/coliving-eval.ts`（新建，批量 runner + 阶段二的结构性检查，
  风格照抄 `scripts/search-eval.ts`：`--limit`/`--concurrency`/
  `--scenario <id>` 这类参数，输出到终端也输出一份 JSON 报告）
- `package.json`：加一条 `"coliving-eval": "cross-env
  NODE_OPTIONS=--conditions=react-server tsx scripts/coliving-eval.ts"`，
  跟其他 eval 脚本对齐
- `CLAUDE.md`：评测脚本那张表加一行 `coliving-eval`，写清楚"盯的是
  什么、什么时候值得跑"
- `.claude/AGENT_LOG.md`：记一条"从一次性脚本迁移到语料库+批量 runner"
  的决策记录，说清楚为什么、怎么改的、旧的一次性脚本模式正式弃用

## 执行时的大致节奏（这份文件被真正启用之后）

1. 用户说"按这个文件干活"，我先确认现状有没有变化（模型/DB/部署），
   再动手，不是无脑照抄
2. 从阶段一开始做，先把 25 轮里已经验证过的场景迁移成语料文件、
   建好 runner，跑一次全量确认迁移没有引入偏差（跟原来 25 轮的结论
   对得上）
3. 阶段二的结构性检查跟着建，因为收益最直接、风险最低
4. 阶段三、四按实际需要的量再上——如果语料库还只有几十条，人工审查
   一遍也不慢，不用为了"未来可能需要"而现在就把子代理并行审查这套
   建起来
5. 阶段五（语料库只增不减）从阶段一建成的那一刻就该生效，不是最后
   才补的

## 不做什么

- 不为了并行而并行——如果某次只需要测 1-2 个新场景，直接跑，不用
  绕经语料库+批量 runner 这套流程，那是给"超级多测试用例"这个场景
  准备的，量小的时候现在的单线流程完全够用，甚至更快
- 不引入额外的 CI/编排系统（GitHub Actions 之类）——除非用户明确要
  自动化跑批这件事本身（比如"每天自动跑一遍语料库"），否则这就是
  一个本地脚本，跟其他 eval 脚本一样"按需手动跑"
- 不为了追求"更真实"而在语料库里存脱敏不完整的生产对话——生产
  事故要收回语料库，先手动改写成不含真实号码/真实人名的干净版本，
  参照现在测试脚本里全部用 `+1555...` 假号码这个已有的纪律
